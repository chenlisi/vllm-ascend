# 评审规则表（Reviewer 子 agent）

> **用途**：供 Reviewer 子 agent 的脚本 A（`review_scope.py`）按文件路径 glob 匹配；在 Phase 4 工作流中作**步骤 3 的复查清单**——先读源码出意见、再用本表逐条补漏（见 `.claude/agents/reviewer.md`）。
> **来源**：① `AGENTS.md`（vLLM Ascend Development Guidelines）的硬约束；② 同一仓 `reviewer-dev` 分支上 **798 份真实已合并 PR 的评审报告**（`.agents/skills/vllm-ascend-reviewer/references/reports/`）里的人工/机器评审原话与检查点，经**清洗去噪**后归并为条目。每条规则附来源 PR 供追溯。
> **来源列取值**：`AGENTS.md` / `评审要点 B`（流程硬约束）、`PR<编号>`（真实已合并 PR）、`PR<编号> 相关发现`（该 PR 报告中的次要发现）、`规则库`（由多条同类条目抽象，未绑定单一 PR）。
> **多来源的语义**：一条规则挂多个 PR，表示**同一模式在多个 PR 反复出现**（跨 PR 合并），不是某单个 PR 的结论；反之，**一个 PR 也可支撑多条规则**——其报告往往提出多个主题（如 PR2167 的报告同时要求「复用既有实现」「给出长期维护策略」「不直接 import 其他文件的全局变量」「仓库级问题另开 PR」）。故**不可**用「536 条聚类摘要」反推来源是否误挂：该摘要是**有损派生**（535/536 条仅保留 1 个 PR 且只留单一主题），只作检索索引，**追溯须以原始报告为准**。
> **口径**：严重度分三档——`阻断`（合入前必须解决）/`重要`（应解决）/`建议`（可选改进）。分级召回策略见 `DESIGN.md` 7.5：阻断级高召回、建议级高精度。
> **规模**：14 组、共 302 条；覆盖来源的 16 个类别。
> **本表的使用位置**：步骤 2 **先读源码出意见**（此时不展开本表）；步骤 3 再用本表**逐条复查**——补漏 + 剔除与历史**未被采纳**意见同型的噪音。**本表用于复查，不作为评审的起点。**

## 使用方法

1. 脚本 A 据改动文件路径匹配所属分组（一个文件可命中多组），输出该文件适用的规则集，落 `scope.json`。
2. **步骤 2 读源码出意见**（见 `reviewer.md`）——凭源码与判断力直出意见，**此步不展开本表**，免得评审变成照着清单勾选。
3. **步骤 3 复查**——用本表逐条回查：历史反复出现的问题有没有被漏掉？漏检项补入 findings，并附**证据**（`文件:行号` 或机器可读信号）。
4. 本表**不覆盖**的部分（逻辑错误、跨文件语义、设计意图、领域精度直觉）本就不该指望它——由步骤 2 承担，见 `DESIGN.md` 8.3。

## 清洗说明（哪些来源条目被剔除）

从 536 条来源规则中剔除了以下类型，以免污染规则表：

- **描述被截断**（如 PR9531 的 `rule.description` 只有半句）；
- **占位 / 空值条目**（`adoption_judgment` 为空、`_status = pending_llm_extract`）；
- **非评审意见的噪声**（如 `"@zzzzwwjj @whx-sjtu"`、`"rebase to main and remove this section directly"`、`"need reconstruct this."` 等沟通流水）；
- **已在其他条目覆盖的重复项**（同一 PR 在多类别重复出现，如 PR12491 出现在 4 个类别）；
- **过窄的一次性条目**（只在某个 PR 的特定上下文成立，泛化后无检查价值）——其中仍可复用的思路经人工抽象后进入 `review-heuristics.md`，不在此表逐条罗列。
