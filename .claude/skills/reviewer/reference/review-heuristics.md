# 评审思路（Reviewer 子 agent）

> **用途**：Phase 4 工作流**步骤 2「读源码出意见」的提问参考**——先按这些思路把源码里真看到的问题问出来；命中与否都不预设结论。
> **与 `review-rules.md` 的关系**：本文件是**提问参考**（不绑定文件路径，回答"该往哪想、该问什么"），用于**步骤 2**；规则表是**复查清单**（按文件 glob 匹配、逐条可核对），用于**步骤 3**。顺序是**先读源码、再用规则表复查**。
> **来源**：由 `review-rules.md` 的 302 条规则与同仓 `reviewer-dev` 分支 798 份真实评审报告**人工抽象**而来；每条思路的「支撑来源」给出规则编号，可回 `review-rules.md` 查到对应的真实 PR。**不引入任何未经来源支撑的新结论。**
> **规模**：14 组、共 50 条。
> **纪律**：发散不等于放言。建议级问题仍须**有证据**（`文件:行` 或机器可读信号），**无证据即剔除**；阻断级走高召回、建议级走高精度（见 `DESIGN.md` 7.5）。

## 使用方法

1. **步骤 2 读源码出意见**：对每个改动文件，先读源码，再对**每条思路**问一遍「触发条件是否成立 / 典型问句是否有异常答案」——此步**不展开规则表**；
2. 有异常的，落成 findings（只写 `existing_code` 锚点，行号交脚本 C 回填）；
3. **步骤 3 复查**：再用 `review-rules.md` 逐条回查是否有历史反复出现的问题被漏掉；
4. 思路只负责**提出问题**，是否成立仍须以源码与证据判定——**不得**把「疑似」写成「确认」。

## R1 通用代码规范与风格

### H1-1 改一处，问对称处

- **思路**：对称结构中只改了一半，通常意味着另一半被漏掉——分支、调用点、参数与引用、实现与测试都成对存在。
- **触发**：diff 中出现 `if/elif`、多调用点、重命名、参数增删，但只改了其中一个位置。
- **问句**：与它对称的另一半（分支 / 调用点 / 引用点 / 测试）同步了吗？还有谁在用旧名字/旧签名？
- **支撑来源**：`R1-18`、`R1-20`、`R1-26`、`R1-27`、`R11-19`

### H1-2 名字即契约

- **思路**：命名、类型注解、参数顺序都在向读者承诺语义；改动任一项，代价是「全部引用点 + 全部读者」，不只是本地那一行。
- **触发**：新命名、新参数、多返回值、类型注解、`kwargs` 传递。
- **问句**：这个名字/类型/顺序会让读者理解错吗？它在所有引用点都还成立吗？
- **支撑来源**：`R1-5`、`R1-6`、`R1-9`、`R1-14`、`R1-21`

### H1-3 临时态必带移除计划

- **思路**：一切「临时 / 兼容 / 调试 / 回滚」代码都是负债，唯一合理的形态是「明确写下何时、依据什么删掉」。
- **触发**：注释掉的代码、`if False:`、保留的旧实现、TODO/FIXME、未消费的返回值。
- **问句**：这段代码还有谁能到达？谁会在什么条件下删掉它？
- **支撑来源**：`R1-7`、`R1-8`、`R2-9`、`R14-11`

## R2 注释与 docstring

### H2-1 差异即注释义务

- **思路**：与上游不同、与直觉不同、与常规数值不同的地方，**必须**解释「为什么」，否则后续维护者只能靠猜。
- **触发**：复制上游代码后改动、early-return 与上游行为不一致、非常见数值常量、dtype/布局转换。
- **问句**：这里为什么和上游 / 直觉不一样？原因写下来了吗？
- **支撑来源**：`R2-2`、`R2-6`、`R2-7`、`R2-8`

### H2-2 可读性三问

- **思路**：缩写、术语、命名与行为三者的一致性，是文档与注释的基线；不一致会直接误导读者。
- **触发**：新增缩写、跨文件术语、函数名含 `enable/disable` 等修饰词、同一文件内注释风格混杂。
- **问句**：缩写首现展开了吗？术语全仓一致吗？名字和它实际做的事一致吗？
- **支撑来源**：`R2-5`、`R2-10`、`R2-12`、`R12-9`、`R12-30`

### H2-3 隐含假设显式化

- **思路**：代码里"默认成立"的前提（不变量、前置条件、非空、形状固定）都应写成断言或注释；不写就等于把风险留给运行时。
- **触发**：新增下标访问、shape 假设、`Optional` 参数被直接使用、跨模块共享状态。
- **问句**：这段代码依赖什么默认成立？如果它不成立，会静默跑错还是立刻报错？
- **支撑来源**：`R2-11`、`R1-17`、`R3-18`、`R10-5`

## R3 环境变量与配置

### H3-1 一个开关一个来源

- **思路**：配置项的定义处、读取处、文档处三处必须一致；「同一件事有两处开关」迟早漂移。
- **触发**：新增环境变量 / 配置字段、新增读取方式、`additional_config` 变更。
- **问句**：这个开关定义在哪、由谁读、文档写了吗？有没有第二处也在定义它？
- **支撑来源**：`R3-1`、`R3-2`、`R3-5`、`R13-24`

### H3-2 三态陷阱

- **思路**：`未设置` / `None` / `0` / `空容器` 是四种不同语义；用 truthy 判断会把合法值当缺省值丢掉。
- **触发**：`if x:`、`x or default`、`kwargs.get(...)` 默认 `None` 后直接访问、字典取值。
- **问句**：`0` / `False` / 空列表在这里是合法取值吗？如果是，这个判断会误伤吗？
- **支撑来源**：`R3-7`、`R3-8`、`R3-11`、`R3-18`

### H3-3 配置的组合合法性

- **思路**：单看每项配置都合法，组合起来可能矛盾（主开关关、子开关开）；这类矛盾应在初始化时显式校验并给出可读错误。
- **触发**：新增主/子开关、互斥配置、优先级规则、新增 `_validate_*`。
- **问句**：这些开关的所有组合都合法吗？矛盾的组合会被拦截还是静默走错分支？
- **支撑来源**：`R3-4`、`R3-6`、`R3-17`、`R3-10`

## R4 Patch 与框架适配

### H4-1 patch 生命周期四问

- **思路**：每个 monkey patch 都要能回答「为何打 / 怎么打 / 何时能删 / 上游是否已修」；答不出就是长期负债。
- **触发**：新增或修改 `vllm_ascend/patch/**`、条件启用逻辑。
- **问句**：为什么非 patch 不可（能否 CustomOp / 继承）？上游修了之后由谁、依据什么移除？
- **支撑来源**：`R4-1`、`R4-5`、`R4-8`、`R9-4`

### H4-2 继承与复用优先于替换

- **思路**：能继承就继承，能扩展就不整段替换；重复上游实现既增加维护面，也增加与上游漂移的风险。
- **触发**：新增类、重写 `forward`/`weight_loader`、发现与上游同名实现"看起来一样"。
- **问句**：这段和上游/既有实现是不是重复？为什么不能继承或复用？
- **支撑来源**：`R4-4`、`R4-10`、`R4-11`、`R14-4`

### H4-3 patch 台账联动

- **思路**：patch 是"有台账的资产"——增删 patch 必须同步登记表、导出与段号；台账与代码不一致等于没有台账。
- **触发**：增删/移动 patch 文件、调整 patch 子目录结构。
- **问句**：`patch/__init__.py` 的四段式登记与导出让号同步了吗？移除后段号重排了吗？
- **支撑来源**：`R4-2`、`R4-3`、`R4-6`

## R5 算子、精度与硬件适配

### H5-1 数值精度阶梯

- **思路**：精度问题几乎都藏在"中间计算"里——激活/路由/norm 的中间量、门控参数、低秩分解的运算顺序与 dtype，都要与厂商实现等价。
- **触发**：新算子、新激活、norm 改造、低秩（q_lora/kv_lora）路径、dtype 转换。
- **问句**：中间计算是 fp32 吗？门控参数是 float32 吗？与厂商实现的顺序/dtype 等价吗？
- **支撑来源**：`R5-1`、`R5-2`、`R5-3`

### H5-2 硬件能力是运行时事实

- **思路**：算子支持哪些场景、参数有何约束、目标平台可不可用，都是运行时事实而非代码假设；「用了再说」会变成静默错结果或启动失败。
- **触发**：调用融合算子、硬编码硬件参数（UB 偏移、vector core 数）、仅特定硬件可用的功能。
- **问句**：这个算子在这个场景（prefill/decode、tp_size>1）确认支持吗？参数满足算子约束吗？不支持的平台会怎样？
- **支撑来源**：`R5-8`、`R5-9`、`R5-10`、`R5-18`、`R5-20`

### H5-3 设备差异集中化

- **思路**：设备相关的差异应收敛到 `DeviceAdaptor` / `DeviceOperator` 一类专门位置，而不是散落在通用 `utils.py` 或业务逻辑里。
- **触发**：新增平台判断、设备特定分支、修改通用 Linear/工具函数。
- **问句**：这个平台差异应该放在哪里？它会不会污染通用路径或承载业务逻辑？
- **支撑来源**：`R5-12`、`R5-13`、`R5-14`、`R5-15`

### H5-4 Triton 的静态/动态边界

- **思路**：Triton kernel 里"什么在编译期定、什么在运行期定"必须分清——该 `constexpr` 的没标会重编译，该动态的写死会失效，grid 取值口径也要一致。
- **触发**：新增/修改 Triton kernel、`tl.constexpr`、`do_not_specialize`、grid size、`tl.arange`。
- **问句**：这个值运行期会变吗？变了会重编译吗？`tl.arange` 是 power-of-two 吗？
- **支撑来源**：`R5-26`、`R5-29`、`R5-21`、`R6-22`、`R10-15`

## R6 推理、性能与热路径

### H6-1 热路径疑似同步即问

- **思路**：每 step 执行的路径上，任何 host-device 同步或物化拷贝都会被放大成吞吐损失；看到就应质疑其必要性。
- **触发**：`.item()`、`.cpu()`、`.contiguous()`、每步 dtype 转换、`torch.where` 兜底。
- **问句**：这是热路径吗？这个同步/拷贝能不能用预置的 CPU 端元数据或非连续输入替代？
- **支撑来源**：`R6-1`、`R6-2`、`R6-5`、`R6-26`、`R6-23`

### H6-2 每步重复计算都是税

- **思路**：在每 step 路径上，"每次都算一遍"的固定量应改为预计算、缓存或查表；累加起来的开销常被低估。
- **触发**：`torch.arange`、`cumsum`、固定查表、重复构建 metadata。
- **问句**：这个结果每步都一样吗？能不能在初始化时算一次并在后续复用？
- **支撑来源**：`R6-4`、`R6-7`、`R6-24`、`R6-10`

### H6-3 图模式的额外约束

- **思路**：图模式对 CPU 同步、动态 shape/分支、metadata 生成位置都很敏感；在 eager 下正常的写法在图上可能退化或报错。
- **触发**：改动落在图模式路径、attention 模式切换、metadata 构建。
- **问句**：这个写法在图捕获下成立吗？会不会引入动态分支或每步重建？
- **支撑来源**：`R6-2`、`R6-11`、`R6-13`

### H6-4 性能特性默认开

- **思路**：主线已可用的性能能力（fullgraph、cudagraph 等）应默认启用；教程/示例里保留 `enforce_eager` 之类会掩盖真实性能。
- **触发**：教程命令、默认配置、示例脚本。
- **问句**：这里为什么还关着主线已支持的性能特性？是必要还是遗留？
- **支撑来源**：`R6-25`

## R7 分布式与并行

### H7-1 全维度覆盖

- **思路**：并行相关改动要在 TP / PP / DP / CP 四个维度上分别自问"成立吗"；只处理了其中一部分是最常见的漏。
- **触发**：集合通信、并行组创建、跨 rank 逻辑、DP 场景分支。
- **问句**：TP/PP/DP/CP 下分别会怎样？是不是只覆盖了其中一个维度？
- **支撑来源**：`R7-1`、`R7-3`、`R7-10`

### H7-2 跨 rank 一致性契约

- **思路**：集合通信要求各 rank 的 tensor 大小、形状、顺序、下标完全一致；"按实际数量截断"之类优化会直接破坏契约。
- **触发**：`all_to_all`/`all_gather`、`view` 重塑、下标访问变更、通信原语签名变更。
- **问句**：各 rank 的 shape/大小/顺序在这个改动后还一致吗？下标契约上下游对齐了吗？
- **支撑来源**：`R7-2`、`R7-5`、`R7-11`、`R7-12`

### H7-3 通信域与设备的显式化

- **思路**：优先复用已有通信组，显式指定设备，避免隐式 `set_device` 与重复建组导致的通信域不一致。
- **触发**：创建 tensor、创建 TP/DP 通信组、组初始化顺序。
- **问句**：这个通信组能不能复用 WORLD？设备是显式指定的吗？
- **支撑来源**：`R7-4`、`R7-6`、`R7-7`

## R8 KV Cache 与内存张量

### H8-1 场景矩阵穷举

- **思路**：KV / 内存路径的正确性依赖"组合矩阵"——dtype、量化、sparse、cache mode、并行配置；矩阵里每一格都要问一句。
- **触发**：KV cache 分配、block table、量化路径、多模式函数（如 `align`/`none`）。
- **问句**：这个改动在 sparse C8 / MLA / GQA / 各 cache mode 下都成立吗？哪一格的语义不同却被同一段代码覆盖？
- **支撑来源**：`R8-4`、`R8-6`、`R8-8`、`R8-11`

### H8-2 物化拷贝的代价

- **思路**：`contiguous()`、隐式副本、不会被使用的输出张量，在内存受限或大张量场景都会实打实占 HBM。
- **触发**：`.contiguous()`、`clone()`、原地更新的输出张量、格式转换（NZ/FRACTAL）。
- **问句**：这次拷贝/分配真的必要吗？能不能用非连续输入或原地更新省掉它？
- **支撑来源**：`R8-14`、`R8-15`、`R6-23`、`R5-5`

### H8-3 清理的确定性

- **思路**：资源与状态的释放必须走确定性路径（`try/finally`、上下文管理器）；模块级缓存一旦"永久降级"就无法恢复。
- **触发**：上下文管理器、异常路径、模块级可变缓存、能力探测结果缓存。
- **问句**：抛异常时资源还会被释放吗？这个缓存的失败状态会不会永久生效？
- **支撑来源**：`R8-1`、`R8-2`、`R8-3`

## R9 版本兼容与上游同步

### H9-1 兼容分支会过期

- **思路**：为兼容旧版本保留的每个 `if version` / mock / 分支，都有"上游修好之后"的失效时刻；没有移除条件的兼容代码就是永久的维护负担。
- **触发**：`vllm_version_is`、条件 mock、升级 PR、删除旧版本支持。
- **问句**：这个兼容分支还需要吗？上游修了之后由谁删？
- **支撑来源**：`R9-5`、`R9-6`、`R9-8`

### H9-2 版本判定的正确形态

- **思路**：版本比较要数值化、集中化、可注释；字符串前缀匹配与硬编码版本号都是错误形态。
- **触发**：版本判断、安装脚本、CI 中的版本引用。
- **问句**：这里用的是数值比较吗？版本号是集中管理还是硬编码在多处？
- **支撑来源**：`R9-1`、`R9-2`、`R9-7`、`R9-16`

### H9-3 升级 PR 最小变更

- **思路**：升级类 PR 的价值在于"沉浸式跟随上游"；顺手改无关逻辑/测试/配置会让评审无法定位风险。
- **触发**：依赖 / vLLM 版本升级、Python 版本升级。
- **问句**：这一处修改和升级有关吗？无关的是不是该拆出去？
- **支撑来源**：`R9-3`、`R9-11`、`R9-21`

### H9-4 版本引用联动

- **思路**：一个版本号往往同时出现在代码、CI、镜像、文档四处；只改一处会造成"文档说 A、CI 跑 B"。
- **触发**：版本升级、发布说明、CI workflow、Dockerfile、支持矩阵文档。
- **问句**：这次版本变更，代码 / CI / 镜像 / 文档都同步了吗？
- **支撑来源**：`R9-10`、`R9-12`、`R9-19`、`R9-20`、`R13-22`

## R10 错误处理与日志

### H10-1 静默失败是最差形态

- **思路**：被吞掉的异常会让错误在很远的地方才爆发，且丢失现场；兜底分支必须显式 `raise` / 记录 / 返回，而不是 `pass`。
- **触发**：`except` 兜底、`else` 兜底、默认返回值、可选依赖缺失。
- **问句**：这里失败会怎样？谁来发现？错误现场还在吗？
- **支撑来源**：`R10-3`、`R10-9`、`R1-1`

### H10-2 断言 vs 异常

- **思路**：`assert` 在 `-O` 下会消失，不能承担生产校验；配置/输入校验用带信息的 `raise`，断言只用于内部不变量且须带上下文。
- **触发**：配置校验、参数校验、内部不变量、错误消息。
- **问句**：这个校验在生产（`-O`）下还在吗？错误消息说清了触发条件吗？
- **支撑来源**：`R10-4`、`R10-5`、`R3-10`

### H10-3 不要试探

- **思路**：用 `try/except` 探属性是否存在或做条件分支，会掩盖真正的初始化错误并掩盖逻辑意图。
- **触发**：`try/except AttributeError`、防御性 try/except、可选依赖探测。
- **问句**：这里是在探测，还是在处理真实异常？初始化后必然可用的调用需要防御吗？
- **支撑来源**：`R10-10`、`R10-11`、`R10-12`

### H10-4 日志形态与级别

- **思路**：用 `logging` 而非 `print`；用 `%` 格式化而非 f-string；级别与场景匹配；统一前缀走 `LoggerAdapter`。
- **触发**：新增日志、调试输出、错误级别选择、平台日志前缀。
- **问句**：这是该用 error 还是 warning？"捕获但不抛出"的场景用 error 级合适吗？
- **支撑来源**：`R10-6`、`R10-7`、`R10-17`、`R10-20`

## R11 测试

### H11-1 测对对象

- **思路**：测试要测"这次改动真正引入的行为"——融合算子就测融合算子、改的分支就测那个分支，而不是替身实现或空跑。
- **触发**：新增/修改实现、UT 新增、性能/精度路径改动。
- **问句**：这个测试真正断言的是被测对象吗？换个实现（错的那种）它会失败吗？
- **支撑来源**：`R11-2`、`R11-4`、`R11-8`

### H11-2 边界与失败模式是必答题

- **思路**：正常路径的测试只能证明"能跑通"；边界（越界、`None`、空、极端配置）与失败路径才暴露正确性。
- **触发**：新增函数/分支、新增配置项、涉及可选字段与下标访问。
- **问句**：边界与失败模式覆盖了吗？测试取值反映真实取值范围吗（并注明来源）？
- **支撑来源**：`R11-5`、`R11-18`、`R11-20`

### H11-3 测试的登记与分类

- **思路**：新测试/新模型不只是"写个用例"——要注册进 CI 清单、放对目录、对特定平台做隔离，否则等于没跑。
- **触发**：新增 e2e 配置、新模型、平台专有测试、CI 工具。
- **问句**：这个用例被 CI 调度到了吗（注册清单）？目录分类对吗？平台隔离了吗？
- **支撑来源**：`R11-3`、`R11-11`、`R11-12`、`R11-17`

### H11-4 测试也要做减法

- **思路**：没有验证目标的测试、重复逻辑的测试、临时调试用例都应删或合并参数化——测试代码同样承担维护成本。
- **触发**：新增/重构测试、合入前清理、多配置重复用例。
- **问句**：这个用例验证的实质内容是什么？和别的用例重复吗？临时用例清了吗？
- **支撑来源**：`R11-9`、`R11-10`、`R11-13`、`R11-14`

## R12 文档与 Tutorial

### H12-1 文档与代码必须一致

- **思路**：文档里最容易错的不是文字，而是**可执行的细节**——命令、参数取值、模型名、URL、版本号；复制粘贴后必须逐项核对。
- **触发**：教程命令、参数说明、支持矩阵、版本引用、下载链接。
- **问句**：文档里的命令/参数/模型名和实际一致吗？这个命令实测跑过吗？
- **支撑来源**：`R12-3`、`R12-6`、`R12-15`、`R12-27`

### H12-2 复制粘贴的代价

- **思路**：跨硬件系列、跨模型复制文档时，硬件相关取值（TP/DP、环境变量、场景）必须逐项修正，不能只改标题。
- **触发**：新增教程、从既有文档复制、多硬件系列文档。
- **问句**：这份文档是从哪份复制的？里面哪些取值是特定于原硬件/模型的？
- **支撑来源**：`R12-2`、`R12-4`、`R12-32`

### H12-3 可运行性优先

- **思路**：文档的价值在于能被照着跑通；残留 TODO、私有镜像、缺失的依赖/命令都会让文档失效。
- **触发**：新增教程、部署文档、示例脚本。
- **问句**：照着这份文档能一次跑通吗？有没有 TODO 占位、私有镜像、缺失步骤？
- **支撑来源**：`R12-5`、`R12-8`、`R12-26`

### H12-4 占位符与结构规范

- **思路**：涉及真实 IP / 私有路径的内容应改占位符；表格、标题编号、行尾空格等结构问题要走 markdownlint。
- **触发**：新增/修改文档、表格、多平台命令块。
- **问句**：有没有泄漏真实 IP / 私有路径？表格分隔符与标题编号合规吗？
- **支撑来源**：`R12-10`、`R12-11`、`R12-13`、`R12-31`

## R13 构建、部署与 CI

### H13-1 CI 的范围纪律

- **思路**：CI / 构建配置的改动最容易"顺手捎带"；与本次功能无关的流水线改动应剔除或另开 PR。
- **触发**：`.github/workflows/**`、测试配置、Dockerfile 变更。
- **问句**：这处 CI 改动是本次功能必需的吗？无关的是不是该拆出去？
- **支撑来源**：`R13-7`、`R13-31`、`R14-2`

### H13-2 单一数据源

- **思路**：重复的依赖安装块、散落的版本引用、不一致的环境变量，都应收敛到单一来源。
- **触发**：多个 Dockerfile、多个 workflow、版本/环境变量引用。
- **问句**：这块逻辑有没有第二处副本？版本/环境变量是集中管理还是到处硬编码？
- **支撑来源**：`R13-5`、`R13-8`、`R13-12`、`R13-22`

### H13-3 失败必须可见

- **思路**：CI 的价值是"失败即拦"；`continue-on-error`、静默跳过、过宽权限都会让失败不可见。
- **触发**：CI 步骤配置、权限配置、缓存配置、关键参数。
- **问句**：这里失败会被 CI 拦住吗？关键配置的用途注释了吗？权限是最小集吗？
- **支撑来源**：`R13-2`、`R13-15`、`R13-18`

### H13-4 下载与安装的健壮性

- **思路**：构建期的网络下载与包安装是最易碎的环节，重试/超时、正确的 pip 形式、轻量 runner 都是低成本高收益。
- **触发**：Dockerfile 的 `wget`/`curl`/`pip`、CI runner 选择。
- **问句**：这个下载有重试与超时吗？安装用的是 `python3 -m pip --no-cache-dir` 吗？
- **支撑来源**：`R13-3`、`R13-4`、`R13-20`

## R14 工程治理

### H14-1 PR 单一职责

- **思路**：一个 PR 只做一件事；仓库级问题（CI、mypy 配置、无关重构）会在评审中稀释风险判断，应另开 PR。
- **触发**：diff 中出现与 PR 目标无关的文件（尤其配置、CI、其他模块）。
- **问句**：这些改动都服务于这个 PR 的目标吗？无关的是不是该拆出去？
- **支撑来源**：`R14-2`、`R14-5`、`R13-7`

### H14-2 复用优先于重写

- **思路**：与上游或既有实现重复的代码应继承或复用；"能跑"不等于"该写"，重写意味着长期双份维护。
- **触发**：新增类与既有类高度相似、重复的工具函数、直接的跨文件全局变量依赖。
- **问句**：这段和既有实现是不是一样的？为什么不能复用或继承？
- **支撑来源**：`R14-4`、`R14-9`、`R1-19`

### H14-3 承诺必落地

- **思路**：评审/PR 中的"后续会补"必须以可追踪形式落地（清单 + `@owner` + tracking issue），否则等于没承诺。
- **触发**：PR 描述中的 follow-up、TODO、作者回复"we will add it"。
- **问句**：这些 follow-up 有清单、`@owner` 与 tracking issue 吗？能本 PR 改完的是否已经改完？
- **支撑来源**：`R14-3`、`R9-13`

### H14-4 反向判断

- **思路**：评审不只找"缺什么"，也要问"多什么"——无必要的校验、限制、抽象、配置应被质疑并简化或删除。
- **触发**：新增校验/限制/防御逻辑/抽象层、复杂条件判断。
- **问句**：这个校验/限制真的必要吗？更简洁的实现（如直接走 eager）能满足吗？删掉会怎样？
- **支撑来源**：`R14-6`、`R14-8`、`R14-12`
